**핵심 메시지 3줄**

1. **실제 사진 검증이 정적 리뷰로는 절대 못 찾을 결함 3건을 잡았다.** 그중 하나(180° 축 모호성)는 인식률을 **0.013 → 0.338 (26배)** 로 바꾼 단일 원인이었다.
2. **매처 자체는 정상**이다(동일 영상 스코어 1.0). 병목은 매칭이 아니라 **미뉴셔 재현성**이며, 이는 Chowdhury 리뷰 Table 4가 예측한 그대로다(고전 NIST 매처 EER 43.83 % vs 딥 7.93 %).
3. 아키텍처의 **인터페이스 분리는 성공적**이다. 세 차례 결함 수정이 모두 파이프라인 코드를 건드리지 않고 구현체 내부에서 끝났다.

## 3. 아키텍처 리뷰

### 3.1 잘된 점

**① 계약 우선 설계가 실제로 값을 했다**

`include/cfp/abstractions.hpp`의 6개 인터페이스(`IFrameSource`, `IQualityGate`, `IFingerSegmenter`, `IRidgeEnhancer`, `IMinutiaExtractor`, `ITemplateMatcher`)를 먼저 고정하고 구현체를 붙이는 방식을 택했다. 검증 가능한 증거:

- 결함 수정 3건이 **모두** 구현체 내부에서 끝났고 `pipeline.cpp`는 한 줄(마스크 인자 추가)만 변경됐다.
- CLI(`tools/cfp_cli.cpp`)에서 DI 조립부가 **6줄**이다. 절편 교체 지점이 한 곳으로 모였다.

**② OpenCV 의존성 분리**

`cfp_core`(metrics·matcher·narration)는 OpenCV에 의존하지 않는다. 결과:
- 이 환경에서 OpenCV 설치 전에도 매칭/평가 로직을 컴파일·테스트할 수 있었다.
- CI가 가벼워진다(OpenCV 빌드 없이 22개 테스트 실행 가능).

**③ 실패를 예외가 아니라 값으로 다룸**

`PipelineOutput.ok` + `failure_stage`. 초당 30프레임 루프에서 "손가락 없음"은 정상 상태지 예외가 아니다. 테스트로 검증됨:
```
[ ok ] 빈 프레임은 예외가 아니라 실패 상태로 보고 (segment:no skin region)
```

**④ 논문 추적성이 코드에 내장됨** (`narration.hpp` / `narrate_stages.cpp`)

각 스택이 자신이 구현한 논문의 절·원문 인용·예측을 들고 있고, 실행 시 실측값과 대조한 결론을 만든다. 문서와 코드가 따로 노는 것을 구조적으로 막는다.

### 3.2 아쉬운 점

**① `IRidgeEnhancer` 인터페이스를 결국 변경했다**

"인터페이스는 추가만 하고 변경하지 않는다"고 선언해 놓고 `enhance(gray)` → `enhance(gray, mask)`로 바꿨다. 원인은 설계 시점에 **"세그멘테이션이 이미 알아낸 정보를 하류가 재추정하면 안 된다"** 는 원칙을 놓친 것이다. 기본 인자로 하위호환을 유지했지만, 이런 데이터 흐름은 초기 설계에서 잡았어야 한다.

**② 설정 외부화 미구현**

dev_plan V0-µ3이 `appsettings.json`을 요구했으나 현재 모든 설정이 구조체 기본값이다. 임계값 튜닝에 재빌드가 필요하다. 실제 카메라·조명 조합마다 재보정이 필요한 값들(§5 F-08)이므로 우선순위가 낮지 않다.

**③ 단일 스레드**

파이프라인 전체가 순차 실행이다. 프리뷰 30fps 목표라면 획득/처리 분리가 필요하다.

## 4. 실제 촬영 사진 검증 결과 ★

이 절이 이번 리뷰의 핵심이다.

### 4.1 파이프라인 전 구간 통과 (실촬영본)

| 스택 | 실측값 | 판정 |
|---|---|---|
| 획득 | 684×1059, 손가락폭 15 mm 가정 시 **1,159 ppi 등가** | ✅ 500 ppi 충족 |
| 품질 게이트 | 선명도 3.9 / 밝기 140.2 / 대비 59.5 / 포화 17.1 % | ⚠️ **out of focus 차단** (인쇄 도판 확대본이므로 타당) |
| 세그멘테이션 | 주축 −0.0°, 피부 마스크 72.1 % | ✅ 지두 정확히 크롭 |
| 방향장 | 일관성(coherence) **0.991** | ✅ 융선이 국소적으로 잘 정렬 |
| 융선 주파수 | 주기 **7.36 px**, 추정 성공 100 % | ✅ 정상 범위 |
| Gabor·이진화 | 융선 픽셀 42.3 %, 골격 4,332 px | ✅ 균형 정상 |
| 미뉴셔 | **29개** (끝점 7, 분기점 22) | ✅ 정상 범위 |

### 4.2 인식(매칭) 성능 — 변형 조건별 분해

매칭 실패 원인을 매처 탓으로 돌리지 않기 위해 조건을 하나씩 분리해 측정했다.

| 조건 | 미뉴셔 | inlier | 스코어 |
|---|---|---|---|
| 동일 영상 (상한선) | 29 | 29 | **1.0000** |
| 이동만 (+10, −6) | 29 | 29 | **1.0000** |
| 회전 5° | 20 | 14 | 0.3379 |
| 회전 11° | 22 | 15 | 0.3527 |
| 회전 11° + 확대 3 % | 24 | 18 | 0.4655 |
| 회전 11° + 노출변화 | 19 | 11 | 0.2196 |
| 회전 11° + 블러 0.6 | 18 | 12 | 0.2759 |
| **전체 복합** (회전+확대+이동+노출+블러+잡음) | 25 | 8 | 0.0883 |
| **타인** (다른 손가락) | 4 | 2 | 0.0000 |

**해석**

- 매처는 정상이다. 동일 영상과 순수 평행이동에서 **정확히 1.0**이 나온다.
- 단일 변형(회전/노출/블러 각각)에서는 스코어 0.22–0.47로, 타인(0.00)과 **명확히 분리**된다.
- 복합 열화에서 0.088까지 떨어진다. 분리는 유지되지만 운영 임계값을 잡기 어려운 수준이다.
- 병목은 **미뉴셔 재현성**이다. 회전만 5° 줘도 미뉴셔가 29 → 20으로 줄어든다.

**이것이 논문과 일치하는 지점**

Chowdhury & Imtiaz(2022) Table 4는 비접촉 데이터에서 고전 NIST 미뉴셔 매처가 **EER 43.83 %**로 무너지고, 딥러닝 기법이 **7.93 %**를 달성했다고 보고한다. 우리 구현은 그 "고전 기준선"의 자리에 있으며, 관측된 취약성은 리뷰의 예측과 정확히 부합한다. **즉 이 결과는 구현 실패가 아니라 재현 성공이다.**

### 4.3 한계 (정직한 명시)

- **"재촬영"은 모사다.** 물리적으로 두 번 촬영한 것이 아니라 원본에 회전·이동·노출·블러·잡음을 가한 것이다. 실제 재촬영은 3D 자세 변화와 피부 변형까지 포함하므로 **더 어렵다**.
- 원본이 인쇄 도판의 3배 확대본이라 우리 자신의 품질 게이트가 불합격 판정을 냈다. 실제 카메라 원본으로 재검증이 필요하다.
- 피험자 1명, 손가락 1개. 통계적 의미(EER/DET)는 산출 불가.

## 5. 발견된 결함

### 5.1 수정 완료 (5건)

#### F-01 · **치명** · 세그멘테이션 180° 축 모호성 — `src/segmenter_ycbcr.cpp`

**증상**: 같은 사진을 5° 회전시켰을 뿐인데 주축 각도가 `−0.0°` → `175.1°`로 튀고, 미뉴셔가 **29개 → 11개**로 붕괴, 매칭 스코어 0.338 → 0.013.

**원인**: `cv::minAreaRect`의 각도는 **180° 모듈로**다. 수학적으로 `175.1° ≡ −4.9°`지만, 이 값을 그대로 `getRotationMatrix2D`에 넣으면 손가락이 거의 **거꾸로 선다**. 그 상태에서 "위쪽 42 %"를 지두로 크롭하면 실제로는 손가락 **밑동**을 자른다.

**수정**: ① 각도를 `(−90°, 90°]`로 접는다. ② 그래도 남는 상하 반전은 **"손가락 끝이 밑동보다 좁다"** 는 해부학적 사실로 판별한다 — 역회전한 마스크에서 위쪽 1/4과 아래쪽 1/4의 면적을 비교해, 위가 더 넓으면 180°를 더한다.

**효과**: 회전 5° 케이스에서 미뉴셔 11 → 20, 스코어 0.013 → **0.338 (26배)**.

> **이 결함의 교훈**: 정적 코드 리뷰로는 절대 못 잡는다. `rr.angle`을 그대로 쓰는 코드는 읽었을 때 아무 문제가 없어 보인다. **실제 사진을 회전시켜 넣어보는 실험**만이 드러낸다.

#### F-02 · **높음** · 세그멘테이션 마스크가 하류로 전파되지 않음 — `abstractions.hpp` / `enhancer_gabor.cpp`

**증상**: 실촬영본에서 배경이 유효영역으로 새어 들어가 위양성 미뉴셔 발생.

**원인**: `GaborRidgeEnhancer::region_mask()`가 국소분산만으로 유효영역을 **재추정**했다. 세그멘테이션이 이미 "손가락이 어디인가"를 알고 있는데 그 정보를 버린 것. 배경 질감(벽, 그림자 경계)은 분산 테스트를 통과한다.

**수정**: `SegmentResult::roi_mask` 추가(ROI와 동일 기하로 변환, `INTER_NEAREST`로 이진성 유지) → `IRidgeEnhancer::enhance(gray, mask)`로 전달 → 분산 마스크와 교집합.

#### F-03 · **높음** · 세선화가 마스크 경계선을 융선으로 추적 — `enhancer_gabor.cpp`

**증상**: 손가락 윤곽을 따라가는 **가짜 융선**이 생기고, 진짜 융선이 거기 T자로 붙어 존재하지 않는 분기점(CN=3)이 대량 발생.

**원인**: 이진 영상에서 마스크 경계는 큰 연결영역의 테두리다. Zhang-Suen 세선화는 이 테두리를 1픽셀 곡선으로 그대로 추적한다.

**수정**: 세선화 후 침식된 마스크로 골격을 잘라낸다. 골격 픽셀 5,459 → 4,332로 감소, 윤곽 아티팩트 제거 확인.

> 미뉴셔 추출기의 `border_margin`은 **2차 방어선**이지 이 문제의 해법이 아니다. 경계선이 진짜 융선의 CN 값 자체를 오염시키므로 향상 단계에서 끊어야 한다.

#### F-04 · **높음** · 외부 프로세스 타임아웃 부재 — `src/report_pdf.cpp`

**증상**: 이 검증 환경에서 `cfp_cli`가 **2분 넘게 응답 없음**. 실제로 재현됨.

**원인**: `std::system()`으로 헤드리스 브라우저를 호출하며 타임아웃을 걸지 않았다. 디스플레이/IPC가 막힌 환경(CI 컨테이너, 원격 세션)에서 브라우저가 종료하지 않고 매달린다.

**수정**: POSIX는 `timeout(1)` 래핑, Windows는 `CreateProcess` + `WaitForSingleObject(60s)` + `TerminateProcess`. 타임아웃(124/`-2`)을 별도 코드로 구분해 사용자에게 정확한 사유를 알린다. **보고서 생성은 부가 기능이므로 실패해도 앱은 살아 있어야 한다**는 원칙을 적용.

#### F-05 · **낮음** · `wrap_pi` 문서-구현 불일치 — `src/matcher_minutiae.cpp`

헤더는 `(−π, π]`를 약속하는데 구현은 `[−π, π)`였다(`wrap_pi(3π)`가 `−π` 반환). 단위테스트가 잡았다. `< 0` → `<= 0`으로 수정.

> 각도 차이 계산에서 경계는 측도 0이라 실무 영향은 미미하지만, **계약과 구현이 어긋난 것 자체**가 나중에 다른 코드가 계약을 믿고 쓸 때 문제가 된다.

## 7. 테스트 리뷰

### 7.1 결과

```
metrics : 12/12   matcher : 10/10   pipeline : 8/8      합계 30/30
```

### 7.2 테스트가 실제로 잡아낸 것

1. **F-05** (`wrap_pi` 계약 위반) — 단위테스트가 직접 검출
2. **합성 데이터가 비현실적이라는 사실** — 초기 합성 지문은 완전히 연속된 동심 융선이라 미뉴셔가 **4개**뿐이었다. 실제 지문에는 융선이 시작·분기하는 지점이 수십 개다. **위상 특이점(dislocation) 주입**으로 수정(SFinGe 계열 합성기와 같은 원리).
3. **합성 손가락이 대칭 타원이라 F-01을 숨기고 있었다** — 대칭 도형에서는 "끝이 좁다" 판별이 동전던지기가 된다. 해부학적으로 맞게(끝은 둥글고 좁게, 아래로 넓게) 고친 뒤에야 테스트가 실제 사진과 같은 조건이 됐다.

> **가장 중요한 교훈**: 항목 2·3은 **테스트 픽스처 자체가 결함을 은폐하고 있었던** 사례다. 합성 데이터는 "코드가 가정대로 도는가"는 증명하지만 "현실에서 도는가"는 증명하지 못한다. 실제 사진 한 장이 테스트 8개보다 많은 것을 잡았다.

### 7.3 부족한 것

- **스냅샷 회귀 테스트 없음** (dev_plan V4-µ9 미이행). 향상 단계 출력이 조용히 바뀌어도 감지 못한다.
- **성능 회귀 테스트 없음**. 단계별 지연 예산(dev_plan: 고전 경로 ≤ 400 ms)을 강제하는 장치가 없다.
- **EER/DET 산출 미실시**. `cfp_core`에 계산기는 있으나 데이터셋이 없어 실행 못함 → PolyU 확보가 선결.

## 11. 총평

**설계는 검증됐고, 구현은 절반쯤 검증됐다.**

인터페이스 분리와 OpenCV 의존성 격리는 실전에서 값을 했다 — 결함 3건을 고치는 동안 파이프라인 코드가 거의 그대로 유지됐고, OpenCV 없이도 매칭/평가 로직을 먼저 검증할 수 있었다.

반면 **알고리즘 구현은 실제 데이터를 만나기 전까지 신뢰할 수 없다는 것이 이번 리뷰의 결론**이다. 30개 단위테스트를 모두 통과한 코드가, 사진 한 장을 5도 돌리자 인식률이 26배 무너졌다. 그 원인(`minAreaRect`의 180° 모듈로)은 코드를 읽어서는 보이지 않는다.

현재 상태는 **"고전 파이프라인 기준선을 재현했고, 그 한계까지 함께 재현했다"** 이다. Chowdhury 리뷰가 고전 방식의 EER 43.83 %를 보고한 것과 우리가 관측한 취약성은 같은 현상이며, 리뷰가 제시한 해법(딥 세그멘테이션·MinuNet·Siamese)이 왜 필요한지를 **수치로 뒷받침하는 근거를 확보한 것**이 이번 단계의 실질적 성과다.
